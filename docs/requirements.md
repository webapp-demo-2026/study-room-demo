# Requirements — ระบบจองห้องติวของคณะ

ผู้มีส่วนได้ส่วนเสีย: นักศึกษาผู้จอง (รวมผู้ร่วมจอง), เจ้าหน้าที่ดูแลห้อง, อาจารย์ผู้สอน (Stakeholder ที่ดู Sprint Review)
ข้อมูลหลัก 5 ชนิดที่สัมพันธ์กัน: ผู้ใช้ (users), ห้อง (rooms), การจอง (bookings), ผู้ร่วมจอง (booking_participants), ประกาศ (announcements)
ข้อมูลทุกตัวในระบบเป็นข้อมูลสมมติ (ชื่อ รหัสนักศึกษา อีเมล)

## Functional Requirements (ระบบต้อง "ทำ" อะไร)
| รหัส | ความต้องการ | ผู้ใช้ | ตรวจได้โดย |
|---|---|---|---|
| FR-01 | ระบบต้องให้นักศึกษาลงทะเบียนด้วยชื่อ รหัสนักศึกษา และอีเมลของมหาวิทยาลัย แล้วเข้าสู่ระบบด้วยอีเมลและรหัสผ่าน; บัญชีเจ้าหน้าที่สร้างไว้ล่วงหน้าและเข้าสู่ระบบแบบเดียวกัน | ทั้งสองบทบาท | ลงทะเบียนด้วยอีเมลนอกโดเมนมหาวิทยาลัยแล้วถูกปฏิเสธ |
| FR-02 | ระบบต้องค้นหาห้องว่างตามวันที่ ช่วงเวลา และจำนวนคน และแสดงชื่อห้อง ความจุ และอุปกรณ์ของห้องที่ว่างตลอดช่วงนั้น | นักศึกษา | ค้นหา 4 คนแล้วไม่เห็นห้องที่จุ 3 คน |
| FR-03 | ระบบต้องให้นักศึกษาจองห้องว่างครั้งละ 1–3 ชั่วโมง ภายในเวลาเปิด 08:00–20:00 และล่วงหน้าไม่เกิน 7 วัน | นักศึกษา | จอง 4 ชั่วโมงหรือจองวันที่ 8 แล้วถูกปฏิเสธพร้อมข้อความบอกเหตุผล |
| FR-04 | ระบบต้องไม่ยอมให้มีการจองที่เวลาซ้อนกันในห้องเดียวกัน แม้สองคนกดจองพร้อมกัน | นักศึกษา | จองช่วงที่ทับการจองเดิมแล้วถูกปฏิเสธ |
| FR-05 | ระบบต้องให้ผู้จองเพิ่มผู้ร่วมจองด้วยรหัสนักศึกษา โดยจำนวนคนรวมผู้จองไม่เกินความจุห้อง | นักศึกษา | เพิ่มคนเกินความจุแล้วถูกปฏิเสธ |
| FR-06 | ระบบต้องส่งอีเมลยืนยันถึงผู้จองและผู้ร่วมจองเมื่อจองสำเร็จ ส่งอีเมลเตือน 30 นาทีก่อนเวลาเริ่ม และส่งอีเมลแจ้งเมื่อการจองถูกยกเลิก | ทั้งสองบทบาท | กล่องอีเมลทดสอบได้อีเมลครบทั้ง 3 กรณี |
| FR-07 | ระบบต้องแสดงรายการการจองของผู้ใช้ที่เข้าสู่ระบบ และให้ยกเลิกได้จนถึง 1 ชั่วโมงก่อนเวลาเริ่ม | นักศึกษา | ยกเลิกเมื่อเหลือ 50 นาทีแล้วถูกปฏิเสธ |
| FR-08 | ระบบต้องให้เจ้าหน้าที่เพิ่มห้อง แก้ไขความจุและอุปกรณ์ และปิดใช้ห้องชั่วคราวพร้อมช่วงวันที่ | เจ้าหน้าที่ | ห้องที่ปิดใช้ไม่ขึ้นในผลค้นหาช่วงวันที่นั้น |
| FR-09 | ระบบต้องแสดงตารางการจองรายวันของทุกห้องให้เจ้าหน้าที่ และให้ยกเลิกการจองใดก็ได้พร้อมระบุเหตุผล | เจ้าหน้าที่ | ยกเลิกพร้อมเหตุผลแล้วผู้จองได้อีเมลที่มีเหตุผลนั้น |
| FR-10 | ระบบต้องให้เจ้าหน้าที่ลงประกาศที่มีวันหมดอายุ และแสดงประกาศที่ยังไม่หมดอายุบนหน้าแรกของนักศึกษา | ทั้งสองบทบาท | ประกาศที่หมดอายุแล้วไม่แสดง |

## Non-functional Requirements (คุณภาพ — หมวดตาม ISO/IEC 25010:2023)
| รหัส | หมวด (ISO/IEC 25010:2023) | ความต้องการที่วัดได้ | วิธีวัด |
|---|---|---|---|
| NFR-01 | Performance Efficiency (Time behaviour) | หน้าผลค้นหาห้องว่างแสดงครบภายใน 2 วินาทีสำหรับ 95% ของคำขอ เมื่อฐานข้อมูลมีการจอง 5,000 รายการ | จับเวลาจาก DevTools แท็บ Network 20 ครั้งบนข้อมูลทดสอบ |
| NFR-02 | Security (Confidentiality) | นักศึกษาเห็นและยกเลิกได้เฉพาะการจองที่ตัวเองเป็นผู้จอง; การเรียกหน้าการจองของคนอื่นได้ผลปฏิเสธทุกครั้ง; รหัสผ่านไม่ถูกเก็บเป็นข้อความเดิม | ทดสอบด้วยบัญชีทดสอบ 2 บัญชี เปิดลิงก์การจองของอีกบัญชี |
| NFR-03 | Interaction Capability (Learnability) | ผู้ใช้ที่ไม่เคยเห็นระบบจองห้องสำเร็จเองภายใน 3 นาทีโดยไม่มีคนช่วย | สถานการณ์ T-01 ในแผนทดสอบ Usability |
| NFR-04 | Flexibility (Adaptability) | ทุกหน้าของนักศึกษาใช้งานได้ครบบนจอกว้าง 360 px ขึ้นไป โดยไม่มีแถบเลื่อนแนวนอน | เปิดด้วย Device Toolbar ของ DevTools ที่ 360 px ทุกหน้า S-01–S-05 |
| NFR-05 | Reliability (Availability) | ระบบใช้งานได้อย่างน้อย 99% ของเวลา 08:00–20:00 วันจันทร์–ศุกร์ในแต่ละเดือน | บันทึกเวลาที่ระบบล่มต่อเดือน |
| NFR-06 | Interaction Capability (User error protection) | ก่อนยืนยันการจองและการยกเลิก ระบบแสดงสรุปห้อง วัน เวลา และต้องกดยืนยันอีกครั้ง | ตรวจหน้า S-03 และกล่องยืนยันการยกเลิกใน S-05 |

## ข้อสังเกตในการเขียน
- ทุก FR ขึ้นต้น "ระบบต้อง…" และมีวิธีตรวจที่ได้ผลผ่าน/ไม่ผ่านชัดเจน
- ทุก NFR มีตัวเลขหรือเงื่อนไขที่วัดได้ ไม่ใช่ "ระบบต้องเร็ว" หรือ "ใช้ง่าย"
